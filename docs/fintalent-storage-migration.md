# Переход пользовательских файлов FinTalent на S3

Для явно согласованного административного переноса закрытых сертификатов и вложений тестов утилита поддерживает `--private-admin-verification` вместе с `--apply`, `--manifest`, `--journal` и `--app-url`. Режим отказывает публичным источникам и использованию `MIGRATION_APP_COOKIE`. До копирования и после него проверяется запрет анонимного HTTP-доступа; исходник и его владелец проверяются существующим Apply, копия — полным чтением из S3 и SHA-256. Журнал использует отдельный статус `copied_verified_private_admin_checked`; успешное чтение под реальным владельцем этим режимом не проверяется. При ошибке проверки после копирования выполняется существующий адресный возврат на legacy-чтение с сохранением оригинала и S3-объекта. Подмена пользовательских сессий и ослабление прав API не применяются.

## Состояние и границы

Изменения готовятся локально в `feature/academy-object-storage`. Это инструкция по согласованному развёртыванию, а не свидетельство выполненной production-миграции. Production не обновлялся. Резервные копии production ещё не созданы и восстановление их не проверено: требуется выбрать внешнее защищённое место хранения и отдельную облачную PostgreSQL для восстановления. Локальную PostgreSQL не запускать.

Общая конфигурация и официальные источники Yandex: [academy-storage.md](academy-storage.md). Используется один `internal/objectstorage.Store`/S3-адаптер, один bucket и существующие переменные S3. Историческое имя `ACADEMY_STORAGE_DRIVER` сохранено: оно теперь выбирает также режим новых загрузок остальных файловых адаптеров. Секреты остаются только в защищённом окружении.

## Модули

| Модуль | Источник | Совместимость и права |
| --- | --- | --- |
| Аватары | `users.avatar_url`, `static/uploads/avatars` | Прежний публичный URL; профиль ссылается на тот же путь |
| Вопросы тестов | `test_question_materials`, `content BYTEA` | Те же ID, API, приглашения, результаты и проверки доступа; BYTEA не удаляется |
| ПрофиМаркет | solutions/media/regulation sections/items, `static/uploads/profimarket` | Старые URL в JSON/HTML и версиях не переписываются |
| Бухгалтерские компании | `accounting_companies`, uploads/accounting-companies | Владелец файла — компания; загрузивший пользователь записывается отдельно |
| Публикации | publications/versions/series, uploads/publications | Сохраняются встроенные изображения и исторические версии |
| Сертификаты | `resume_education_certificates`, uploads/resume-certificates | Те же ID; GET/HEAD существующего endpoint выдаёт документ только владельцу |
| Академия | `academy_media_assets`, reports, upload sessions | Прежняя интеграция Store/Multipart, доступ по зачислению/уроку; старые local/S3 ключи поддерживаются |
| Иконки справочника должностей | uploads/position-icons | Системный владелец platform; нельзя приписывать случайному администратору |

Обычные файлы сборки `static/`, stock-иллюстрации, vendor, generated assets и временные PDF не являются пользовательскими загрузками и не переносятся как пользовательские объекты.

## Владение и ключи

```
users/{user_id}/academy/{random48hex}
users/{user_id}/tests/{random48hex}
users/{user_id}/files/{random48hex}
organizations/accounting-companies/{company_id}/files/{random48hex}
platform/files/{random48hex}
```

Существуют реальные сущности бухгалтерских компаний с собственным ID. Поэтому их изображения принадлежат компании, а не назначенному менеджеру. Это не создаёт вторую базу организаций или авторизацию. `created_by` хранит загрузившего пользователя, когда он известен. Общие платформенные иконки имеют owner_kind=platform и owner_id=0.

Миграция **090_shared_object_files.sql** добавляет реестр `object_files` и представление `file_storage_usage`. Реестр хранит legacy_ref, владельца, категорию, storage_id=primary, неизменяемый object_key, имя, MIME, размер, SHA-256, статус и lease. Триггер запрещает изменение идентичности и владельца существующего объекта. Смена владельца бизнес-сущности не перемещает объект. Endpoint/bucket/постоянные облачные URL в реестре отсутствуют.

Академия сохраняет собственные метаданные 088/089, а не создаёт дубликаты в реестре. Представление usage объединяет активные известные S3-объекты обоих механизмов. Это логическая атрибуция; multipart, нетекущие версии bucket, исходные локальные копии и ожидающие удаления объекты не равны выставленному провайдером объёму.

## Загрузка и чтение

В переходном режиме небольшие legacy-загрузки сохраняют локальный оригинал, затем копируют его в S3 и проверяют SHA-256 повторным чтением. Тестовые вложения сохраняют также исходный BYTEA. Результат операции не объявляется успешным, если S3-проверка не прошла. Нельзя автоматически удалять эти оригиналы после запуска миграции.

Большое видео Академии по-прежнему идёт браузер → S3 multipart, без записи на сервер приложения. Временные файлы небольших загрузок очищаются. Ограничения существующих модулей не увеличены. Копирование небольшой загрузки ограничено 25 секундами в рамках HTTP-запроса; при недоступности хранилища возвращается ошибка, исходные данные сохраняются для разбора/повтора.

Старые `/static/uploads/...` проходят через общий resolver. Если записи в реестре нет или копирование не завершено, работает прежний локальный файл. Для ready-записи сервер читает из S3, отдаёт те же байты и заголовок `X-FinTalent-Storage: s3`. При отказе S3 ready-запись не переключается молча на диск.

Небольшие файлы выдаются потоково через существующие URL приложения. Это сохраняет same-origin работу редакторов и не пересылает `X-Test-Invitation`/`X-Test-Result` в S3 через браузерный redirect. Защищённые endpoints сначала выполняют прежние проверки доступа. Сам по себе object key, owner_id или registry ID не даёт пользователю доступа. Видео Академии использует короткие presigned GET/Range.

Авторизация тестовых файлов использует ту же SQL-проверку прав. Для готовой S3-записи BYTEA больше не загружается в память при каждом GET; оригинал читается только при legacy-выдаче. PDF результатов тестирования продолжает использовать прежний источник, который сохранён. Ответы, попытки, оценки и версии тестов не обновляются мигратором.

Сертификат скачивается через `/api/v1/resumes/education-certificate?id={id}` после проверки владельца. В собственной форме образования имя сертификата стало ссылкой. Общедоступная выдача сертификатов или расширение прав работодателей не добавлены.

## Nginx и IAM перед переключением

Если production Nginx сам выдаёт `/static/uploads/`, Go-resolver будет обходиться. После согласования нужен отдельный маршрут **в server block FinTalent**, сохраняя URI:

```nginx
location ^~ /static/uploads/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

Это пример для обнаруженного порта FinTalent, а не команда автоматического изменения конфигурации. Проверить фактические include/location, `nginx -t`, затем согласованное применение. Не менять server blocks WebFinChat, общий PostgreSQL или конфигурации соседних сервисов. Не увеличивать upload limits без проверки существующих ограничений; большое видео идёт непосредственно в S3.

Политика backend должна разрешать только необходимые операции над:

```
academy/*                         # прежние ключи
users/*/academy/*
users/*/tests/*
users/*/files/*
organizations/accounting-companies/*/files/*
platform/files/*
```

Bucket остаётся приватным. Публичные изображения доступны через приложение по прежним правилам, bucket не становится публичным. Для live-тестов отдельно разрешается `integration-tests/*`. Backup-учётная запись и backup-хранилище должны быть отделены от backend: доступ backend на удаление исходных объектов не должен давать возможность удалить резервные копии.

## Инвентаризация и dry-run

Команды выполняет администратор с окружением нужной БД. CLI сам не применяет миграции, не запускает сервис и не читает `.env` автоматически. Значения секретов не передавать аргументами команд.

```sh
go run ./cmd/fintalent-storage-migrate \
  --root=/var/www/fintalent.prod \
  --inventory=/PRIVATE_PATH/inventory.json

go run ./cmd/fintalent-storage-migrate \
  --root=/var/www/fintalent.prod \
  --manifest=/PRIVATE_PATH/inventory.json --batch-size=100
```

Первый шаг читает ссылки из БД, файлы только из разрешённых upload-каталогов, считает SHA-256 и пишет закрытый manifest без изменения БД/S3. Второй показывает выбранный пакет без копирования. Manifest не перезаписывается: для повторной инвентаризации нужен новый файл.

Исторический владелец не всегда восстановим из случайного имени файла. Для legacy-копий владелец выводится из ссылок бизнес-записей, поэтому manifest требует проверки администратором. Уже зарегистрированный storage owner имеет приоритет над текущим автором записи. Неоднозначные ссылки помечаются `owner_ambiguous`, невостребованные файлы — `owner_unknown`, отсутствующие/небезопасные пути — соответствующей ошибкой. Их нельзя молча приписывать случайному пользователю или считать успешно перенесёнными.

Разбор таких записей — обязательный пункт перед заявлением о полном переносе. Невостребованные сертификаты тоже попадают в manifest с `record_missing`, а не исчезают из инвентаризации. В production диагностирована одна отсутствующая ссылка на аватар. Ручное исправление manifest допустимо только после установления источника/владельца; не очищать поле problem или SHA-256 ради обхода проверки. Отсутствующий оригинал и изменение его контрольной суммы всё равно блокируют перенос.

Реальные исходные имена сохраняются там, где они есть в БД или реестре. Старые случайные физические имена нельзя достоверно превратить обратно в забытое оригинальное имя загрузки.

## Копирование пакетами и проверка приложения

После backup, восстановления тестовой копии и согласованного развёртывания:

```sh
go run ./cmd/fintalent-storage-migrate \
  --root=/var/www/fintalent.prod \
  --manifest=/PRIVATE_PATH/inventory.json \
  --journal=/PRIVATE_PATH/migration.jsonl \
  --batch-size=100 --app-url=https://fintalent.ru --apply
```

Для следующего пакета используйте `--after` с последним legacy_ref из отчёта. Manifest сортируется по этому полю; дубли и дополнительные JSON-документы отклоняются. Не пропускайте неудавшиеся файлы навсегда: отдельно сформируйте проверенный manifest неудач по журналу и повторите их обработку.

Для каждого источника:

1. Проверяются путь, scope, metadata и контрольная сумма инвентаризации.
2. Резервируется постоянный object key; lease не даёт двум worker одновременно перезаписывать один pending-объект.
3. Данные копируются и полностью проверяются чтением из S3.
4. Только после этого реестр становится ready.
5. GET через прежний URL приложения проверяет статус, заголовок S3 и SHA-256 ответа. Это обнаруживает в том числе обход resolver через Nginx.
6. При ошибке проверки приложения включаются legacy-чтения, но только после проверки сохранённого оригинала. Сбой хранилища/проверки приложения останавливает пакет. Ошибка отката отмечается отдельно и требует остановки/разбора.

Для закрытых файлов требуется законная сессия владельца/уже разрешённого проверяющего в защищённом окружении `MIGRATION_APP_COOKIE`. Cookie не указывается аргументом и не пишется в журнал. Клиент проверки не следует redirect, чтобы не отправить cookie стороннему хосту. Мигратор не подменяет пользователей и не создаёт обход авторизации. Для сертификатов сессия должна принадлежать владельцу; пакеты можно разделить по владельцам. Отсутствие подходящей сессии означает непрошедшую проверку, а не успешную миграцию.

Повторный запуск сверяет источник и remote SHA-256 без создания новых объектов для ready-записей. Новые загрузки после развёртывания уже проходят общий writer, поэтому перенос legacy может идти параллельно. Перед завершением повторить инвентаризацию и сверку журнала; при смене провайдера/схемы записи нужны согласованное окно и остановка новых файловых операций/дренирование workers.

Материалы Академии копируются существующей отдельной командой `cmd/academy-storage-migrate` с её собственными метаданными/проверками; она не меняет ID и не удаляет оригиналы. В диагностированной production-базе активных legacy-материалов Академии не было. Её применение согласовывается отдельно, не запускается автоматически общим мигратором.

## Откат

```sh
go run ./cmd/fintalent-storage-migrate \
  --root=/var/www/fintalent.prod \
  --manifest=/PRIVATE_PATH/inventory.json \
  --journal=/PRIVATE_PATH/rollback.jsonl --rollback --batch-size=100
```

Возвращается только механизм чтения выбранных legacy-файлов. Перед переключением проверяются наличие и SHA-256 оригинала/BYTEA. S3-объекты, исходные файлы и строки результатов не удаляются. Остальные файлы не затрагиваются. Для Академии нельзя просто поставить всем driver=local: новые большие видео никогда не находились на сервере, им нужен отдельный проверенный обратный перенос перед откатом.

## Backup и проверка восстановления — обязательный отдельный этап

Не считать перечисленные действия выполненными, пока нет проверенных архивов и отчёта восстановления.

1. Выбрать внешнее защищённое хранилище и отдельную облачную PostgreSQL для restore. Доступы вводятся администратором вне чата. Не использовать public schema работающей dev/production-базы как цель восстановления.
2. Снять `pg_dump -Fc` именно БД FinTalent, без изменения общей PostgreSQL и без `pg_dumpall`. Сверить версии сервера/pg_dump/цели восстановления: на production обнаружена служба PostgreSQL 18, восстановление на более старую major-версию нельзя считать гарантированным. Передавать поток по SSH в зашифрованное защищённое внешнее хранилище. Дамп содержит персональные данные и password hashes. Пароли/DSN брать из защищённого окружения, не из аргументов. Для восстановления ролей/ownership отдельно сохранить безопасный перечень требуемых ролей, без секретов.
3. Скопировать static/uploads, uploads, data, сохранённый private Academy-каталог, если появится, текущий бинарник, systemd unit/override и относящийся к FinTalent Nginx-конфиг. `.env` хранить только в зашифрованной резервной копии с ограниченным доступом. Секреты не включать в обычный manifest/логи.
4. Согласовать границу согласованности БД и файлов. Пока идут записи, один tar и отдельный pg_dump не гарантируют взаимно согласованный snapshot. Нужны повторная файловая сверка и короткое согласованное ограничение файловых изменений/очистки либо подходящий согласованный snapshot. Не останавливать общий PostgreSQL/WebFinChat. Техническое окно/маршруты ограничений перед выполнением проверяются отдельно.
5. Посчитать SHA-256 архивов и сделать manifest. Проверить, что копии читаются именно вне production, а не являются ссылками на исходный сервер. Независимые резервные копии не заменяются bucket versioning.
6. В изолированной облачной БД восстановить dump с остановкой при ошибке, сверить строки/связи/версии/результаты, восстановить файловую копию в отдельное закрытое окружение и проверить приложение. Не копировать production .env в запуск тестового сервера: заново задать отдельный DATABASE_URL, bind на localhost, безопасный email mock/отсутствие реальных SMTP credentials. При восстановлении будущего S3-снимка использовать отдельный тестовый bucket либо отдельные read-only credentials источника: фоновые GC/worker восстановленного приложения не должны получить право удалить production-объекты. Не запускать тестовый сервер до проверки этой изоляции.
7. Только после положительного результата представить протокол и согласовать production-деплой/копирование. Не менять пользователей, ответы и оценки ради прохождения проверки.

После S3-перехода резервировать БД и объекты независимо, сохранять object keys и Content-Type, проверять контрольные суммы. Смена провайдера требует первоначального copy, delta-sync, дренирования upload sessions/GC, проверки manifest, переключения конфигурации и сохранения исходного bucket на период отката.

## Проверки и ограничения

Автоматические тесты покрывают Store/SDK mock, новую схему PostgreSQL, общий реестр, actual HTTP upload/download handlers, прежние URL, owner-only сертификаты, права на тестовые материалы, неизменность BYTEA, ownership компаний, повтор копирования и откат. Отдельные browser checks Академии используют тестовые API и проверяют видео/перемотку/обновление URL; live S3-тесты используют только integration-tests/*.

`TestSharedFilesLiveS3IsolatedPostgres` прошёл с реальным Yandex Cloud: загрузки через обработчики и проверка шести URL приложения (аватар, публикация, ПрофиМаркет, компания, сертификат, вопрос теста). Данные БД — отдельная временная схема, дисковые оригиналы — временный каталог. Test-only Store wrapper помещает физические объекты исключительно под integration-tests/{run}/, сохраняя проверку логических users/organization keys. Cleanup удаляет только ключи, записанные самим тестом. Это HTTP/API-проверка, не браузерная авторизация. При включённом bucket versioning нетекущие версии после обычного DELETE могут сохраняться согласно политике администратора; массовая очистка версий не выполняется.

Не заявлять, что production переключён, пока не выполнены backup/restore, production HTTP smoke через фактический Nginx и сверка каждого файла. Не заявлять новый полный браузерный прогон всех модулей на основании одних HTTP-тестов. Невостребованные/неоднозначные файлы, отсутствующие источники, неподходящая сессия, ошибки checksum, Nginx обходящий resolver и неготовые резервные копии блокируют завершение полного перехода.
# Уточнения проверок и ограничений

Если передан `MIGRATION_APP_COOKIE`, origin `--app-url` должен совпадать с `APP_BASE_URL`. Cookie нельзя передавать в аргументах команд или сохранять в журнале. Скрытые файлы, обход путей и публичные источники без world-readable разрешения не копируются автоматически: требуется проверка владельца и прежней доступности.

Backend добавляет точные origins S3 в собственную report-only CSP для connect/media. Enforced CSP reverse proxy проверяется отдельно. Внутренний PDF-экспорт тестов сохраняет чтение исходного BYTEA для совместимости; BYTEA сохраняется и при новых загрузках. Это переходное дублирование для отката.

Прошли `go test ./...`, `go vet ./...`, frontend build, изолированные PostgreSQL-тесты общего реестра и вложений тестов, HTTP-проверка шести модулей с реальным S3. Полный браузерный вход и пользовательский сценарий всех модулей, production backup и изолированное восстановление на этом этапе не выполнены.
