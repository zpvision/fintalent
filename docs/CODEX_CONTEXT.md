# CODEX_CONTEXT — быстрая карта FinTalent

Актуально на 2026-09-02. Это не changelog и не полный каталог API. Постоянные правила разработки находятся в корневом `AGENTS.md`.

## Текущее устройство

FinTalent — один Go-процесс и одна PostgreSQL БД. `main.go` открывает глобальный `*sql.DB`, готовит схему/demo data, регистрирует страницы и API в `http.DefaultServeMux`, затем раздаёт гибридный frontend: уже перенесённые React-маршруты и legacy HTML из `static/`. Сервер следует запускать из корня репозитория из-за относительных путей.

Архитектура переходная:

- auth, admin, профиль специалиста (`resume`), survey, география, публикации, ПрофиМаркет и часть marketplace находятся в корневом `package main`;
- тесты (`internal/testmodule`) и вакансии (`internal/vacancymodule`) разделены на domain/dto/repository/service/handler;
- клиентская биржа и бухгалтерские компании выделены в `internal/clientexchange` и `internal/accountingcompany`, но используют общие user/admin resolvers через корневые adapter-файлы;
- новые модули не должны автоматически становиться поводом мигрировать старые.

Frontend поэтапно переносится на React 19/Vite/React Router без редизайна. React-приложение находится в `frontend/src`, собирается в игнорируемый `static/react/`, а Go выдаёт его для всех пользовательских и административных маршрутов. На React-маршруты переключены `/`, авторизация, `/profile`, каталоги, вакансии и профили специалистов, `/marketplace*`, `/profimarket*`, `/client-exchange*`, `/accounting-companies*`, тестовый блок, списки/аналитика/редактор публикаций и `/admin*`. Публичные статьи `/publications/:slug` намеренно остаются серверными из-за SEO-метаданных и JSON-LD. Профиль полностью управляется React, включая меню и секции вакансий, настроек, ПрофиМаркета, компании, клиентской биржи и помощи коллегам. Мастер заполнения профессионального профиля, редактор регламентов, редактор публикаций и админка пока используют legacy compatibility-controller внутри React host. Если build отсутствует или задано `REACT_FRONTEND=false`, Go безопасно возвращает соответствующий legacy HTML. Полная карта и правила перехода находятся в `docs/REACT_MIGRATION.md`.

Legacy frontend остаётся набором HTML/CSS/vanilla JS-файлов. Общая шапка в legacy внедряется `site-header.js`, общий перехват неожиданных fetch/browser ошибок — `site-errors.js`, выборы переиспользуют `searchable-select`, geography и duty picker. `npm run build` собирает и публикационный Editor.js bundle, и React; `npm run dev:react` запускает Vite с proxy на Go.

## Основные модули и связи

Общие release-механизмы: `request_security.go` оборачивает mux (Origin/Fetch Metadata, доверенные proxy CIDRs, bounded process-local rate limit, API body/deadline/no-store). `admin_sessions.go` хранит отдельные хешированные admin tokens с серверным сроком и отзывом, независимо от user sessions. `notification_outbox.go` хранит письма в PostgreSQL и доставляет двумя workers с leases/retries; критичные заявки записывают outbox в общей transaction. Не возвращать синхронный SMTP в HTTP handlers. Runtime pool/shutdown/readiness находятся в `runtime_lifecycle.go`. SQL 065–068 подключены через prepare; миграция 044 применяется после создания таблиц test module. Production требует готовую React-сборку либо явный REACT_FRONTEND=false.

- Users/sessions — основа ownership во всех кабинетах. Admin использует отдельную сессию и `ADMIN_LOGIN`/`ADMIN_PASSWORD`.
- Dictionaries/surveys — метаданные анкет вакансий и профилей специалистов. Универсальные `dictionaries`/`dictionary_items`, block settings, importance и icons используются обоими конструкторами; duties, ОКВЭД, geography и test categories — специализированные справочники.
- Стандартные иконки ответов задаёт `046_dictionary_icon_defaults.sql` через `prepareVacancyModuleDatabase()`: сопоставление по alias справочника и значению ответа, без зависимости от ID или сортировки. Файлы находятся в `static/icons/`; загруженные иконки в `static/uploads/` нужно сохранять при деплое.
- Resume — профиль пользователя с требованиями/знаниями, опытом, образованием, языками, финансовыми и рабочими предпочтениями. В опубликованный resume агрегируются результаты тестов с настраиваемой видимостью. `users.profile_mode` задаёт сценарий `job_search` или `professional`: профессиональный режим скрывает карьерные шаги мастера, но сохраняет их данные и публикует страницу специалиста; выбор доступен после регистрации и в настройках.
- Vacancy — сохраняет требования из тех же категорий справочников, обязанности и выбранные тесты. `internal/vacancymodule/matching` сравнивает требования вакансии с категориями resume; публичная выдача находится отдельно в `vacancy_public.go`.
- Tests — версии тестов, вопросы/ответы, попытки, scoring, публикация и admin moderation. Его используют marketplace, вакансии, resume knowledge и employee testing; не создавать локальные копии модели теста.
- Перемешивание ответов задаётся через `shuffle_answers` теста и хранится в `test_versions` (миграция `047`); `domain.PrepareAnswerOrder` задаёт стабильный порядок по ID попытки для обычного и employee testing. Начало попытки возвращает вопросы её версии; frontend использует этот порядок. `question.settings.shuffle_answers` в ответах API сохраняется только для совместимости.
- Employee testing — сотрудники компании, приглашения и результаты. Результаты также питают паспорт компетенций бухгалтерской компании.
- Publications — статьи/серии, реакции, сохранения, аналитика, модерация и SEO routes. Контент хранится блоками; Editor.js bundle преобразует legacy block format, backend очищает HTML.
- ProfiMarket — каталог решений/регламентов с большим конструктором карточки, заказами/покупками и собственными справочниками.
- Courses — `internal/courses` и адаптер `courses_module.go`, схема `070_courses.sql`. Категории используют общий справочник `course_categories` (есть включение/выключение); профиль преподавателя берётся из `users` и публичного resume через `course_instructors`. Программа, преимущества, бонусы и FAQ — отдельные таблицы; идентификаторы модулей/уроков сохраняются при редактировании. Цена хранится в копейках. PUT черновика проверяет `revision` и атомарно сохраняет структуру; конфликт вкладок возвращает 409. Статусы: draft → moderation → published; скрытие — hidden, редактирование опубликованного/ожидающего курса возвращает draft. Модерация доступна в `/admin/courses`. Публичный API выдаёт только опубликованные курсы незаблокированных авторов; owner preview и admin preview используют тот же React-компонент `CourseView`. Мастер — `/profile/courses/{id}/edit`, кабинет — `/profile/courses`. Платежей, выдачи уроков и прогресса пока нет; отзывы подготовлены в БД, UI показывает только реальные опубликованные записи. Промо-видео открывается внешней HTTPS-ссылкой.
- Настройки курсов: `course_categories` и `course_features` управляются существующим CRUD справочников через вкладки меню «Курсы». Возможности связаны с курсами через `course_feature_selections`; `course_feature_bindings` сохраняет специальные значения certificate/chat/updates/any_device/corporate при переименовании вариантов. API использует `feature_ids`; старые boolean-поля сохраняются для совместимости. Миграция `072_course_settings.sql` переносит прежние флаги в связи, хранит `bonuses_color`. Цветовые ключи преимуществ и бонусов используют общий каталог `static/profimarket-style-presets.js`.
- Текущая коммерческая модель Решений: «покупка» отправляет заявку и контакты автору, без оплаты на сайте. Исторические API/таблица purchases и статус COMPLETED сохраняются для совместимости; они не доказывают платёж, amount — цена автора, не выручка. Эквайринг — отдельная будущая задача. Превью карточки не является защищённой платной выдачей.
- Паспорт опубликованной компании намеренно показывает имена сотрудников и индивидуальные результаты. До прохождения теста сотруднику и при публикации компании владельцу показывается предупреждение об этой публичности. Это продуктовая настройка, не заключение о юридическом соответствии.
- Client exchange — продажа/передача клиентской базы: объявления, module-specific dictionaries, отклики, избранное, статусы и уведомления.
- Accounting companies — профиль/каталог компании, направления, услуги, тарифы, отзывы и competency passport; связан с владельцем-user и результатами employee testing.
- Help — взаимопомощь специалистов вокруг resume: admin topics, публичные направления, заявки requester↔expert, сообщения, завершение, отзывы и уведомления.

## БД и запуск схемы

Во всех локальных запусках, тестах и проверках проекта используется только удалённая облачная PostgreSQL из `DATABASE_URL` в локальном `.env`. Локальную PostgreSQL использовать нельзя; приложение завершает запуск, если `DATABASE_URL` не задан, и локального DB fallback нет. Полную строку подключения, логин и пароль запрещено переносить в документацию, исходный код, логи или Git; `.env` остаётся локальным секретом.

Миграционного runner с журналом версий нет. `prepareDatabase()` вызывается на каждом старте и последовательно запускает inline idempotent DDL и явно подключённые embedded SQL-файлы. Поэтому наличие файла в `migrations/` не гарантирует исполнения. При добавлении схемы обязательны три связи: `//go:embed` → выполнение в `prepare<Module>Database()` → вызов из `prepareDatabase()`.

Исторические `001_schema.sql`/`002_dictionaries.sql` и некоторые следующие файлы отражают схему, но ранние части также создаются inline в Go. Номера `011`, `012`, `040`, `041` повторяются. Не пытаться нормализовать историю в рамках feature-задачи. Demo seed включён по умолчанию и отключается `SEED_DEMO_DATA=false`; синхронизация географии отдельно зависит от `SYNC_GEOGRAPHY`.

Файловые загрузки сохраняются локально (главным образом под `static/uploads/`, сертификаты также под `uploads/`). Production deployment обязан сохранять и давать права записи этим каталогам; объектного хранилища нет.

## Важные особенности API и UI

- В пользовательских текстах сущность resume называется «Профиль». Технические имена `resume`, маршруты `/resume` и `/resumes`, API и таблицы сохраняются для совместимости.
- Одновременно действуют `/api`, `/api/v1`, `/api/public` и `/api/admin`; это не единая новая версия API.
- `docs/openapi.yaml` описывает преимущественно testing API, а не весь продукт.
- Большинство удалений бизнес-сущностей мягкие: status/deleted_at. Перед физическим удалением справочника нужно проверять ссылки.
- Error response обычно `{"error": ...}`, но в историческом коде есть несколько локальных JSON helpers; переиспользовать helper текущего слоя.
- Общая шапка legacy заменяет первый прямой `<header>` в body. В React тот же DOM и поведение реализует `SiteHeader` внутри общего layout.
- `site-errors.js` monkey-patch-ит `window.fetch`; локальные fetch wrappers работают поверх него. Не устанавливать ещё один глобальный patch.
- Многие страницы имеют собственные большие CSS-файлы и дополнительные polish/fix/responsive layers. Сначала выяснить фактический порядок `<link>`, затем менять самый релевантный слой; не сливать их попутно.
- Внешние Google Fonts используются страницами напрямую. React-страницы сначала подключают существующие page CSS без изменения дизайна; консолидация допускается только после визуального сравнения.

## Активные и незавершённые части

- В текущем рабочем дереве есть незакоммиченная разработка модуля помощи: `help_module.go`, `migrations/045_help_module.sql`, admin/profile/resume help assets и интеграционные правки в `main.go`, resume/public pages. Это пользовательская работа: не откатывать, не перезаписывать и учитывать при изменении тех же файлов.
- `publicationSummaryStub` (`/api/publications/summary`) явно является заглушкой. Не считать его готовым summarization service и не расширять без отдельной задачи.
- Архитектурное выделение features в `internal/` выполнено лишь частично; это осознанно зафиксированное текущее состояние, не самостоятельный backlog на массовый рефакторинг.
- Для Академии есть `scripts/academy-browser-check.cjs` (собранный React, headless Edge, изолированные API). Остальные UI требуют проверки desktop/mobile; `go test ./...`, `go vet ./...`, `go build ./...` остаются серверными проверками по масштабу изменений.

## Быстрый маршрут для следующего агента

Для feature-задачи сначала открыть `main.go` (место регистрации), корневой `<feature>_module.go` или ближайший аналог, соответствующий `internal/<feature>` и точные HTML/CSS/JS страницы. Для схемы проверить не только SQL-файл, но и embed/prepare chain. Для справочника сначала изучить `admin.go`, `survey.go`, `duties.go` и module-specific admin CRUD. Для UI сначала проверить общие assets и порядок подключённых stylesheet/script в конкретном HTML.
- Доступ к курсам: миграция `074_course_access.sql` создаёт закрытый по умолчанию режим (`course_access_settings.public_access=false`), индивидуальное разрешение — `users.courses_access`. Админка: «Пользователи → Курсы» и «Курсы → Доступ → Открыть курсы всем». `internal/courses/access.go` проверяет страницы, API и upload; admin-сессия имеет доступ всегда, auth/ownership остаются обязательными для изменения курсов. `/api/courses/access` сообщает текущему посетителю доступ для скрытия ссылок и React gate. Открытый режим разрешает публичный просмотр гостям; индивидуальные разрешения сохраняются для возврата к закрытому режиму.

## FinTalent Academy

- Этап A — `internal/academy` + `academy_module.go`, миграция `078_academy.sql`, React `pages/academy`. Вход из «Мои курсы», маршрут `/profile/courses/:id/academy`, API `/api/academy/courses/:id/*`. Используются существующие сессия владельца и gate доступа к курсам.
- Учебная программа полностью независима от маркетинговых `course_modules/course_lessons`: явное однократное копирование либо пустая программа. Ревизия и транзакции защищают весь граф; изменения Академии не переводят лендинг в черновик.
- Рабочее дерево — `academy_course_programs/modules/lessons/lesson_blocks`; `academy_program_versions` содержит append-only структурированные снимки со стабильными ключами уроков и ID файлов. Потоки с Этапа D ссылаются на версию, прогресс — на зачисление/версию/key урока, без дат открытия в самом уроке.
- `academy_media_assets/academy_asset_links`: закрытый `ACADEMY_STORAGE_DIR` (по умолчанию `.local-data/academy`), никогда не static. Выдача через авторизованный API владельца либо ученика с действующим зачислением и ссылкой файла в его версии/уроке, до 20 МБ. Нужны постоянный каталог, backup и proxy-лимит 21m+. Файлы сохранённых версий не удаляются.
- Текст — имеющийся Editor.js с ограниченным набором инструментов и bluemonday на сервере; общий `LessonRenderer` для предпросмотра и учебной комнаты. Тест привязан к версии существующего теста автора. Прохождение тестов и сдача/проверка работ реализованы Этапом C; потоки, расписание и CRM реализованы Этапом D.
- Автосохранение сериализовано, поздние ответы объединяют только IDs/revision; резервная копия — sessionStorage. Проверки: Academy unit tests, Academy-сценарии внутри изолированного `TestCoursesIsolatedPostgres`, `scripts/academy-browser-check.cjs`. Подробности API и эксплуатации — `docs/ACADEMY_STAGE_A.md`.

- Этап B — `079_academy_learning.sql`: append-only `academy_version_releases` с замороженными метаданными тестов, `academy_enrollments` (право доступа отдельно от завершения, nullable будущий cohort_id), `academy_lesson_progress` и `academy_learning_events`. Прогресс относится к зачислению/версии/key урока; редактирование черновика не меняет обучение.
- Автор публикует снимок и выдаёт доступ существующему пользователю на `/profile/courses/:id/academy/students`; поиск — точный email либо имя публичного профиля, без общей базы пользователей. Авторский preview room не создаёт зачисления.
- Ученик: `/profile/learning` и `/profile/learning/:enrollmentId`, API `/api/academy/learning`, `/api/academy/enrollments/:id/*`. Выданное обучение проверяет зачисление независимо от beta gate каталога; меню доступно участникам курсов либо имеющим зачисление. Не раскрывать программу при приостановке/отзыве/истечении.
- Серверный прогресс — обязательные опубликованные уроки опубликованных модулей. Manual работает после открытия; materials без видео требует явного подтверждения ученика; video/materials без надёжного трекинга блокирует завершение; обязательные тесты и задания учитываются по серверным результатам Этапа C. Невыполненные обязательные требования остаются в знаменателе; без обязательных уроков 0%, без автоматического завершения. Проверка готовности перед публикацией.
- Коллекции обучения/учеников — cursor before=id, до 200 записей на запрос; frontend загружает страницы для фильтрации/сортировки. Проверки B: `academy_learning_integration_test.go` в изолированной облачной схеме и `scripts/academy-learning-browser-check.cjs` (built React + API fixtures, 360/900/1440). Контракты/запуск — `docs/ACADEMY_STAGE_B.md`.

- Этап C — `080_academy_assessments.sql`: `academy_assessment_versions` хранит append-only полную конфигурацию блока и закрытые вопросы/ответы, захваченные транзакционно при снимке программы. Старые версии A/B требуют явного действия владельца «Подготовить проверки этой версии»; существующие определения не заменяются.
- Общий движок оценивания — `internal/testmodule/domain.Grade`, выделенный из профессионального Service.Finish без изменения формулы. Академия использует те же модели вопросов, скрытие решений, стабильное перемешивание и React Review, но отдельные `academy_test_attempts`; профессиональные результаты/рейтинг не меняются. Deadline, лимиты и ревизии контролирует сервер; завершённые попытки защищены триггером.
- `academy_assignment_submissions`: черновик/отправка/проверка/доработка/принято/отклонено, номер попытки, версия, reviewer/назначение. Отправленное содержимое и окончательные решения неизменяемы; `academy_submission_reviews` — append-only аудит с критериями/источником manual/automatic/ai. Доработка создаёт новую попытку; черновики не раскрываются преподавателю. Самопроверка владельца запрещена.
- Ответные файлы — тот же закрытый `academy_media_assets`, nullable submission_id, MIME/лимит 20 МБ и общая выдача; права проверяют зачисление и конкретную попытку. Файлы ответов исключены из авторской библиотеки материалов. События — `academy_learning_events`, уведомления — общая notifications + `/api/academy/notifications`.
- Кабинет преподавателя `/profile/courses/:id/academy/reviews`, очередь/панель с переходом к следующей работе, реальные показатели и результаты тестов. API `/api/academy/courses/:id/reviews*`, `assessment-results`; ученик — `/api/academy/enrollments/:id/lessons/:key/assessments/:block/*`. Renderer уроков общий, интерактивность передаётся только в контексте ученика; предпросмотр не создаёт попыток.
- Завершение требует все обязательные проверки; принятие/тест пересчитывают прогресс атомарно. Лучший либо последний результат определяется снимком; неудачная пересдача в режиме последнего может вернуть урок в процесс. Автоматическое принятие задания проверяет только форматы, без балла/критериев и без заявления об оценке качества; ИИ не включён. Контракты и ограничения — `docs/ACADEMY_STAGE_C.md`; тесты — academy_assessment_integration_test.go и scripts/academy-assessments-browser-check.cjs.

- Этап D — `081_academy_cohorts.sql`: потоки с опубликованной версией, JSONB расписанием/дедлайнами, IANA timezone, вместимостью и ревизиями. Nullable cohort_id зачисления получил составной FK; самостоятельное обучение сохранено. Версия блокируется после первого зачисления; перевод сохраняет старое зачисление/результаты и создаёт новое без копирования прогресса.
- `academy_cohort_staff/student_curators` + SQL `academy_can_manage_enrollment` ограничивают преподавателя потоком, куратора — назначенными зачислениями, проверку — can_review. Область применяется к прежним students/reviews/results/files и новым CRM. Авторский редактор/лендинг сотрудникам не открывается; исключение из бета-gate только для назначенных рабочих разделов (включая HTML-вход).
- `academy_student_notes/tags/student_tag_assignments` — внутренние заметки с ревизией/мягким удалением/аудитом и метки в рамках курса. `academy_student_metrics` рассчитывает показатели и отставание из настоящих результатов; заметки и метки ученику не выдаются.
- Доступность по расписанию проверяется на backend для room/уроков/прогресса/файлов/тестов/заданий. Правило урока приоритетнее модуля, нижняя граница — старт подтверждённо запущенного потока. Относительные дни календарные, не 24-часовые; DST gap/fold отклоняются для локального ввода. Сдача после запрещённого дедлайна блокируется; срок/опоздание фиксируются в отправке, версия задания не меняется.
- `academy_cohort_events` — аудит/идемпотентная очередь in-app уведомлений; расписание отменяет старые pending-события. Доставку раз в минуту запускает существующий lifecycle приложения с context/WaitGroup; транзакция notifications + delivered_at и SKIP LOCKED защищают от дублей. Автоматического запуска scheduled-потоков нет: владелец подтверждает запуск.
